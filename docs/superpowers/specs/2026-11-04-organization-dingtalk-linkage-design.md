# 组织架构与钉钉联动设计

日期：2026-11-04。本文保留最初的分阶段设计。后续已实现手工触发的来源拉取、编号映射、逐项选择应用与人工维护；实际实现采用现有组织版本元数据及私有审计文件，未新增下文拟议的独立 DocType。自动定时应用与事件订阅仍未实施。详见 [本地实现与试验说明](../../acceptance/2026-11-04-organization-dingtalk-linkage.md)。真实钉钉根层只读检查通过；未部署到内网，未完成真实全量导入验收。

## 目标和现状

让人事在组织架构页发现钉钉部门及人员变化，经审核后更新系统部门和组织配置，避免重复维护、同名误配、改名后重复建部门、人员归属被覆盖。

本次代码检查确认：

- `dingtalk_integration.sync_departments_from_dingtalk` 从根部门逐层调用 `department/listsub`，写入带公司范围的原始来源与同步日志；`queue_dingtalk_directory_sync` 已提供后台组织员工拉取入口。
- `dingtalk_organization_review.preview_organization` 原先按部门名称比较已保存来源与启用的 Department。原始记录逐条更新，不能天然代表某一次完整组织快照。
- `organizational_chart.get_hybrid_tree` 当前返回人工组织配置树；后面的部门树逻辑并非当前执行路径。仅同步 Department 或原始记录不会直接重建页面所展示的管理层级。
- `organization_roster_sync` 已提供花名册和主数据变更后的组织引用重建能力。未来应用变更应复用此能力，保持人工组织关系。
- 现有花名册代码已区分“实际部门”与钉钉通讯录多部门归属；联动必须保留该业务边界。

截图可见的展示问题：公司横幅占据图上方较大区域、卡片在当前视口有裁切、展开后横向跨度较大。截图不足以判断其运行时原因，布局优化另列验收，不把数据联动视为布局修复。

## 数据职责

| 数据 | 建议主数据来源 | 联动规则 |
| --- | --- | --- |
| 部门外部编号、通讯录名称、父部门编号 | 钉钉来源快照 | 保存原值；映射后审核新建、改名、移动 |
| 系统 Department 标识 | 人资系统 | 使用稳定文档 ID；改名不产生新映射 |
| 通讯录成员、多部门、部门主管标记 | 钉钉 | 作为来源事实与建议，不直接等同 HR 主部门或正式任命 |
| 员工实际部门、调岗生效日 | 人资系统有效人事流程 | 钉钉差异进入待处理项；调岗流程落账 |
| 分管、课组线管理关系、代理、兼任 | 人资组织配置 | 手工维护、审核发布；可关联外部部门但不强制成为钉钉部门 |
| 编制、空缺、职级、审批权限 | 人资系统 | 不由通讯录部门或主管标记自动推导 |
| 离职、停用、删除 | 人资有效流程及明确来源核实 | 通讯录缺失仅为异常线索 |

员工身份使用 `(corp_id, userid)` 与公司范围内 Employee 映射；工号仅作辅助核对，并检查重复与缺失。钉钉官方明确工号在企业内可能重复，不能当作唯一身份。手机号、姓名不得单独作为自动匹配依据。

第一期继续以现有单一钉钉设置的公司范围运行。未来多公司、多企业应用要先拆分连接配置，不能仅在 UI 增加公司下拉框。

## 建议联动流程

1. **读取来源**：人事从现有“钉钉集成”后台拉取，生成独立快照；记录企业、公司、根部门、授权范围、开始/结束时间、完整性和错误。
2. **核对映射**：已有稳定映射优先；同名和全路径只作候选。新映射须由授权人确认；改名后仍用原部门编号查找。
3. **生成差异草稿**：分为新增、改名、上级变化、成员变化、来源缺失、映射冲突、本地独有。展示当前值、建议值、来源时间、受影响人数和组织节点。
4. **审核选择**：逐条选择采用、保留本地、忽略本次；冲突须写原因。不能把整批默认勾选的建议当成已审核。
5. **预览影响**：检查循环、跨公司引用、停用部门、员工主部门、编制统计、任职和组织节点位置。展示组织树调整前后差异。
6. **应用并重建**：通过 Department 正常保存校验、人事流程和组织配置接口写入；提交后按公司排队重建引用并通知页面刷新。
7. **记录结果**：保存操作者、审核者、原因、来源快照、每条前后值、成功/失败与重试关系。失败必须可见，不显示整批成功。

初次导入与日常联动分开：初次允许生成待发布组织配置草稿，保留当前已发布版本；日常只改已映射对象。禁止在普通页面读取或后台拉取时覆盖已发布配置。

## 待新增的数据模型

### Organization External Department Map

- 连接标识、公司、corp_id、external_department_id、local_department。
- 唯一约束：同一连接与企业内外部部门只能绑定一次；一期同一系统部门只绑定一个外部部门。多对一合并若有业务需求需独立设计，不能隐含支持。
- 状态：待确认、已绑定、停用；保存来源路径快照、确认人、确认时间、原因、最后核对批次。
- 服务端校验本地部门所属公司、读写权限和禁用状态；映射失效时阻止应用。
- 公司根节点 `dept_id=1` 明确映射 Company 或指定系统根容器，不能按名称自动新建一个普通部门。

### Organization Source Snapshot / Item

- 快照头：连接、公司、企业、拉取范围、任务、起止时间、状态、完整性、异常与数量。
- 快照明细：该批次不可变的部门原始字段及标准化字段、父编号；对原始快照施加与组织管理相同的访问限制。
- 只有请求全部完成、分页结束、未触发深度截断、编号唯一且父链有效，才允许标记“范围内读取完整”。
- 完整仅相对于已记录的授权范围。权限范围缩小、根节点变化与异常数量下降必须阻断自动应用；先核实范围。
- 当前 Raw Record 是逐条更新来源；未来不能把它拼接为历史快照。新的独立快照明细需与拉取事务边界配套实现。

### Organization Change Set / Item

- 快照 ID、基线组织版本、差异摘要与指纹、有效期、审核状态；明细含映射 ID、变更类型、当前值、建议值、影响对象、处理决定及原因。
- 应用前重新检查来源指纹、当前 Department/Employee/Organization Node 的 modified 和组织版本；任一变化使预览失效并要求重算。
- 幂等键由公司、快照、变更项和目标组成；同一项只生效一次。应用时按公司串行，数据库唯一约束防止并发重复新建。
- 审核与应用均在服务端校验角色、公司及目标写权限。前端隐藏按钮不构成授权。

## 差异处理规则

| 场景 | 建议处理 |
| --- | --- |
| 相同外部编号，名称改变 | 生成改名项，保留部门映射及业务引用 |
| 相同外部编号，父部门改变 | 生成移动项；展示整棵受影响子树，验证无环后审核 |
| 同名不同编号 | 展示双方完整路径，人工绑定；不自动合并 |
| 外部新增部门 | 先审核映射或新建；必要时加入“待放置”列表 |
| 本地独有部门 | 保留；可为筹备部门或授权范围外部门，不据此删除 |
| 已绑定部门在来源中消失 | 比较范围一致的完整快照后提示疑似缺失；核实后归档，不自动删除 |
| 员工属于多个钉钉部门 | 保存全部通讯录成员关系；HR 主部门仍由有效档案与调岗流程决定 |
| 钉钉主管与当前负责人不同 | 提示任命差异；任职审批前保留现状，不修改权限 |
| 部门重建后编号改变 | 新旧编号人工迁移映射；保留映射历史，不按相同名称继承 |
| 拉取失败、范围变化、空列表、深度上限 | 标记不完整或异常，保留已发布组织，阻止应用 |

当前拉取代码到达 `max_depth` 后会跳过后续层级，可能仍显示完成；完整快照阶段必须修正为明确“不完整”。此次只读增强不改变已有拉取流程，不能据现有“已完成”日志证明全量完整。

## 组织配置和显示层

将通讯录树与管理架构作为两种有明确标题的视图：

- **管理架构**：保留当前 Organization Node，展示分管、代理、兼任、编制；部门节点关联系统 Department。
- **钉钉通讯录**：未来基于指定完整快照展示原始部门层级与成员，只读，并显示来源时间和授权范围。
- **差异核对**：当前本地版本已增加入口；未来接入稳定编号映射、筛选、审核及发布。

同一 Department 在管理架构中出现多处时，每个节点明确“主展示/引用展示”。人数统计按 Employee ID 去重；分别展示“直属人数”和“含下级人数”。兼职成员不重复计入全公司实际人数。空缺与超编分开：空缺=max(编制-实际,0)，超编=max(实际-编制,0)。

布局建议：公司信息用紧凑摘要条；默认只展开到课级；选中节点居中并提供定位根节点；搜索展示路径并展开祖先；右侧详情固定宽度，避免遮挡画布；“一览全局”用于定位，提供可读比例返回键。用截图对应的真实数据和窗口尺寸验证裁切、缩放与展开性能后再验收。

## 同步频率和写回边界

一期优先使用现有内网主动拉取：提供手工刷新；定时拉取组织来源可建议每 30–60 分钟运行，但默认关闭并允许配置，实际频率按额度和组织规模确认。每天进行一次范围一致的完整校验。此方案不依赖公网回调。

二期需要及时性时接入部门、用户变更事件。事件只触发去重后的重拉任务；先验证事件来源、解密或验签、防重放、记录事件 ID，再读取最新详情。事件可能重复或乱序，不能直接按事件覆盖正式组织。事件接入方式与网络条件需单独确认。

暂不默认双向写回。后续确有“在人资审批后发布到钉钉”的需求时，单独启用字段级写入权限与出站队列，使用审核后的命令、幂等、回读确认和失败重试；避免入站更新再次触发出站循环。部门、人员不同字段必须各有唯一主数据来源。

## 实施阶段与验收

### 本次已实现

- 架构图/层级通讯录工具栏向 HR Manager、System Manager 提供“钉钉组织核对”。
- 查询保留服务端钉钉管理权限与公司检查，读取已保存来源，不发起外部写入。
- 双方路径、候选匹配依据、处理建议、本地未匹配部门；循环及缺失父链可读提示。
- 非对象来源及编号内容冲突计为无效来源；提示多批次和未验证完整快照。
- 重复点击防护、离开页面或切换公司后的迟到响应忽略、失败提示和重试能力。

### 下一阶段：快照与稳定映射

完成新模型、迁移、完整性与范围验证、根节点映射、同名/改名映射审核和差异预览。先只读试运行，使用真实授权范围核对新增、改名、移动和成员数量。

### 再下一阶段：审核应用与组织联动

完成变更集、预览指纹、并发校验、权限检查、幂等、日志与补偿方案；先在测试公司验证，再选择少量实际部门试运行。组织配置新增节点先待放置，已存在节点保留人工分管及代理关系；自动重建仅更新已确认引用。

涉及部门树与组织节点的同组结构变更应原子提交；若跨业务流程无法原子完成，明确标记部分失败并重试未完成项。回退通过保留的前后值生成补偿草稿，经冲突检查再审核，不能覆盖后来生效的调岗或任命。

验收必须覆盖：同名不同路径、部门改名不重复建档、移动防环、根映射、跨公司拒绝、重复应用、并发修改导致预览过期、半途失败、范围缩小、深度截断、通讯录多部门、调岗审批、停用部门、手工分管代理不丢失、切换公司无串数据。

本地纯逻辑测试与脚本验证不等同真实 Frappe 权限、数据库迁移、后台队列或钉钉连通验收。
