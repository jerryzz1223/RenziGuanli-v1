# 组织架构：钉钉首次建立、人工维护及后续合并

日期：2026-11-04。状态：本地实现及模拟钉钉来源的真实 Frappe 回滚试验通过；额外通过现有接口完成真实钉钉根层只读连通检查。未部署内网，未完成真实全量来源及应用验收。

## 使用方式

System Manager 在组织架构图或层级通讯录中点击“从钉钉建立／同步”。

1. 点击“拉取最新钉钉部门”。后台从根部门逐层读取当前应用授权可见的部门，等待结束后显示来源列表。来源缓存 30 分钟；过期后重新拉取。
2. 关联现有组织节点和系统部门。相同名称只生成候选；采用该行后才形成持久编号映射。需要独立新建时勾选“明确新建节点”。同名钉钉部门须分别选择可区分的系统部门。
3. 首次建立可点击“全部选择采用”；已有架构默认“保留人工结果”，逐项选择“采用钉钉名称与上级”。
4. 点击“校验并预览”，查看当前名称、当前上级、来源名称、来源上级编号，以及是否存在人工调整。
5. 填写原因并点击“应用所选变化”。确认提示会说明采用来源将覆盖所选节点的人工名称及位置。应用后刷新架构图，可继续使用“编辑组织节点”和拖动等现有操作人工加工。
6. 后续重复以上流程；来源缺少的部门保留，未选中的节点保留。若预览后组织或部门已经变化，服务端拒绝旧预览，要求重新预览。

钉钉设置需要正确的同步公司、CorpId、应用凭证及 API 启用状态，后台需要可消费 long 队列的 worker。这里只增加部门组织来源读取；员工档案导入继续使用既有钉钉员工同步流程，图中成员读取系统花名册。

## 实现边界

- 新模块 `hrms.api.organization_dingtalk_linkage` 负责后台拉取、用户/公司/连接范围的缓存来源、差异预览和应用。
- 每个企业部门编号关联当前组织版本中的节点 ID。映射、上次应用的名称/上级基线和已应用批次保存在 Organization Structure Version.notes 中。现有 notes 中其他选项保留，不要求新增 DocType 或数据库迁移。
- 已映射部门更名仍定位到原节点。未映射的同名节点仅为候选。正常关联不能直接改绑；原节点被删除或停用后，可明确选择新建或其他节点修复断开的关联。
- 新建节点使用通用“部门”类型，支持任意正常部门名称；相关显示、详情、手工编辑、成员范围及配置导入导出支持该类型。
- 采用来源只更新所选组织节点的显示名称和上级，保留其编制、代理、任职等其他字段。已有 Department 名称和上下级、Employee 档案均不改写。无匹配系统部门的新节点会创建可关联的 Department；组织展示树与业务部门树仍为两个层次。
- 手工维护及花名册刷新沿用原流程；同步不会替用户开启组织的花名册自动更新选项。
- 缺失来源不触发删除/停用。读取空树、缺失上级、重复编号、循环、异常响应、深度/数量截断均拒绝应用。
- 合并后再次检查整棵“人工关系 + 选中来源关系”是否成环；新增下级必须同时采用尚未建立的来源上级。
- 应用按公司和组织版本串行，并锁定节点、部门，通过当前读重新比较完整状态指纹；防止并发人工修改被覆盖。同一批次重复提交返回已应用结果，不再次新建节点。
- 应用失败回滚该批业务变更；私有 JSON 记录来源、处理决定、原因、操作者和每个变化的前后值，附在组织版本上。记录提供审计证据，本轮未增加“一键回滚”按钮。
- 当前为手工触发、逐项选择的单向来源合并，不会自动定时应用，也不会写回钉钉。本地站点原有图谱入口仍有永新专用公司别名规则；本轮未扩展成通用多企业产品。

## 本地验证

纯 Python 测试 47 项通过：

- `test_organization_dingtalk_merge.py`：12 项，覆盖默认保留、名称/位置人工变更、缺失来源、重复编号、缺失上级、混合树循环、错误关联、跨连接、来源响应及指纹。
- `test_organization_roles.py`：9 项。
- `test_organization_roster.py`：7 项。
- `test_dingtalk_organization_linkage.py`：4 项。
- `test_dingtalk_assets_20261028.py`：15 项。

5 个前端脚本通过：新联动流程、只读核对、既有人工组织行为、配置完整性、待匹配配置。另通过 JavaScript 语法和差异格式检查。前端脚本使用 VM 和模拟 Dialog，未做真实浏览器点击验收。

`organization_dingtalk_linkage_runtime_check.py` 在本地 Docker Frappe `hrms.localhost` 中使用真实 Document 校验、数据库事务、Redis 缓存与私有 File，钉钉 HTTP 响应为模拟数据：

1. 后台拉取函数递归读取模拟部门，状态从 queued 到 ready；来源拉取和预览均不修改架构。
2. 首次建立两个层级的节点及部门，架构树数据能够读取通用“部门”节点；相同批次重试不重复创建。
3. 调用正常人工编辑接口修改名称、位置及编制。
4. 第二次来源更名并新增部门，只采用部分变化；人工名称、位置和编制保留。
5. 预览后再做人工修改，旧预览被拒绝；重新预览并明确采用后，名称和上级更新，编制仍保留。
6. 模拟应用中途审计失败，组织修改回滚；来源缺失部门不删除。
7. 未写入员工档案，审计文件为私有文件。
8. 最终回滚测试公司、部门、节点、版本及映射，清除缓存夹具及测试文件。

试验为隔离测试公司跳过了无关的公司会计初始化，并将站点的永新专用公司别名解析限制到测试公司；应用、节点保存和结构读取使用真实代码。测试直接调用后台函数，没有验证实际 worker 消费任务、真实钉钉权限/额度/授权范围、真实浏览器表现或生产环境。

另行检查本地连接：集成和 API 模式已开启，公司、Client ID、Client Secret 已配置，但 CorpId 未填写；未输出任何凭证。调用现有 `fetch_dingtalk_departments('1')`，真实响应的根层下级列表包含 1 条部门记录，说明该接口当前可达。未输出部门名称、未保存来源、未应用组织变化，并回滚该检查事务。此结果只证明根层读取，不证明全量可见性。新联动流程要求补齐正确 CorpId 后才能建立稳定映射，避免不同企业的相同部门编号混用。

## 上线核对

部署这些文件并更新前端资源后，以 System Manager 验证入口；确认 worker、同步公司、CorpId、凭证和通讯录可见范围。首次在测试公司或受控部门范围中核对来源，再应用组织变化。已有组织优先关联节点，避免在原图旁重复建立同名结构。本次没有执行部署、迁移或修改内网业务数据。
